# Résumé guide (for the AI and the red ! tips)

The résumé editor reads this file. The red ! tips follow these rules, and the AI uses them when it suggests a rewrite.
Each rule says where it comes from. Never invent experience, employers, dates or numbers: when a number would help, ask the owner for it or use a placeholder like [N] that he must fill in.

## How résumés are read
- A recruiter's first pass is very short: about 7.4 seconds in The Ladders' 2018 eye-tracking study. Simple layouts with clear section headings, bold titles and bulleted accomplishments held attention; cluttered pages, multiple columns, long sentences and missing headings hurt. [Ladders 2018, via HR Dive]
- Before a person reads it, an applicant-tracking system (ATS) usually parses the PDF into fields (contact, jobs, dates, education, skills) and lets recruiters search it by keywords. Single-column layouts with standard headings parse most reliably; tables, text boxes, multiple columns and text inside images are the common causes of broken parsing. [ATS vendor and career-service guidance]

## Structure
- Contact on top: name, phone, email, city/country, LinkedIn, and for developers GitHub and a portfolio link. Missing contact details is a top mistake. [Harvard OCS; Google recruiters]
- Standard headings: Summary, Experience, Projects, Education, Skills, Languages. Unusual headings confuse an ATS.
- Newest first inside each section. Order sections by what matters most for the target job. [Harvard OCS]
- Length: one page for early-career profiles; keep it concise and easy to skim. [Google recruiters; Harvard OCS]
- For technical roles, list programming languages and engines prominently and include a GitHub link. [Google recruiters]
- Photo: common in Israel, but leave it out for US/UK and most international applications (Harvard OCS advises no photo, no age, no gender).
- No "References available upon request". No personal pronouns ("I", "my"). [Harvard OCS]

## Bullets
- Start every bullet with a strong action verb (Built, Designed, Implemented, Optimized, Led, Shipped, Reduced, Automated). Avoid passive phrasing and weak openers like "Responsible for", "Helped", "Worked on", "Participated in". [Harvard OCS]
- Show impact with the X-Y-Z formula: "Accomplished [X] as measured by [Y], by doing [Z]". Quantify when possible: players, FPS, load time, build size, team size, deadlines, % improvement. [Google recruiters / Laszlo Bock]
- One to two lines each; 3–5 bullets for the main job, 2–3 for older jobs and projects. Long sentences lower engagement. [Ladders 2018]
- Same tense per role: present tense for the current job, past tense for past jobs and finished projects.
- Specific beats generic: name the engine, language, system and result ("Built a ScriptableObject dialogue system with branching…" beats "Worked on game systems").

## Game developer specifics
- Link each project to something a recruiter can open in one click (portfolio page, video, itch.io, Steam, GitHub).
- Say your role on team projects (programmer, producer, designer) and the team size and length.
- Skills: group them (Engines, Languages, Tools, Practices). Put the engine the job asks for first.
- Mention shipped / playable / jam results and anything measurable (performance, players, ratings, deadlines).

## Matching a job ad
- Tailor the résumé for each job: use the exact words the ad uses for skills you really have (e.g. "Unity", "C#", "multiplayer", "UI Toolkit"), in Skills and inside the bullets where you used them. [Harvard OCS; Google recruiters]
- Never add a skill you don't have. If a must-have is missing, tell the owner instead.
